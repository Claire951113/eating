## 3. 在 VS Code 內完成編輯、建置與執行

本說明統一以 **Windows 的 VS Code 內建 PowerShell 終端機**操作為例。編輯程式、輸入建置指令、玩遊戲及查看測試結果，都在同一個 VS Code 視窗內完成。(會建議在VScode內是因為比較方便，但如果你有習慣的作業環境也沒有問題~)

1. 先將作業壓縮檔完整解壓縮。
2. 在 VS Code 選「檔案 → 開啟資料夾」，選取解壓縮後的 **`student_starter`**，不要只開啟單一 `.c` 檔。

4. 選上方「終端機 → 新增終端機」，在下方面板輸入指令。
5. 查看終端機類型；若不是 PowerShell，可在終端機面板右上方「＋」旁的下拉選單選擇 PowerShell。

終端機是用文字指令操作電腦的地方。編輯區用來寫 C 程式，下方「終端機」用來輸入 `make` 等命令；請點入終端機後再輸入。

第一行顯示目前路徑，應以 `student_starter` 結尾；第二行列出檔案，應包含 `Makefile`。**編輯區正在開啟哪個檔案，不會自動改變終端機的工作資料夾。**


請換成自己電腦的實際路徑，路徑有空白或中文時保留引號。提示字元如 `PS C:\...\student_starter>` 是終端機顯示的資訊，不需要跟著輸入。

### 3.2 確認編譯與建置工具

先在同一個 VS Code 終端機內確認 GCC：

```powershell
gcc --version
```

接著確認 Make 指令名稱。**找不到 `make`，不一定代表未安裝 Make。** 在終端機輸入：

```powershell
Get-Command make,mingw32-make,mingw64-make -ErrorAction SilentlyContinue
```

依結果選一個可用名稱，執行對應的版本查詢；不需要三個都安裝。也可開啟 MinGW 安裝位置的 `bin` 資料夾，查看實際執行檔名稱，再使用下表對應的指令。
(建議去\mingw64\bin裡，看檔案名稱是make.exe、mingw32-make.exe、mingw64-make.exe的哪一個，沒意外的話應該會是mingw32-make.exe。你有兩種做法，第一種是複製相同檔案並改名為`make.exe`，這樣你就可以使用`make`指令。第二種是指令改為使用`mingw32-make`)

| 找到的執行檔 | 查詢版本 | 建置遊戲 | 執行測試 | 清理產物 |
|---|---|---|---|---|
| `make.exe` | `make --version` | `make` | `make test` | `make clean` |
| `mingw32-make.exe` | `mingw32-make --version` | `mingw32-make` | `mingw32-make test` | `mingw32-make clean` |
| `mingw64-make.exe`（若工具包提供） | `mingw64-make --version` | `mingw64-make` | `mingw64-make test` | `mingw64-make clean` |

**本文後續以 `make` 統稱 Make 指令。若你可用的是 `mingw32-make` 或 `mingw64-make`，請在所有操作中一致替換開頭的 `make`，後面的 `test`、`clean` 等參數照寫。** 不需要重新命名執行檔，也不需修改專案的 `Makefile` 檔名或內容。

若已知道工具的完整路徑，但 `Get-Command` 找不到，可先用 PowerShell 的 `&` 呼叫，例如：

```powershell
& 'C:\mingw64\bin\mingw32-make.exe' --version
& 'C:\mingw64\bin\mingw32-make.exe' test
```

請換成自己電腦的實際路徑與檔名，並確認工具所在資料夾已加入 PATH；只指定 Make 的路徑，仍需確保它能找到 GCC。

VS Code 是編輯器，PowerShell 是執行命令的介面；真正編譯 C 程式的是 GCC，依規則建置的是 GNU Make。安裝 VS Code 或 C 語言擴充套件，不代表已安裝 GCC、Make。

若顯示找不到命令，請確認 GCC 與 GNU Make 已安裝，且工具所在資料夾已加入 PATH；安裝或調整環境後，完整關閉並重新開啟 VS Code，再新增終端機確認。

### 3.4 在終端機執行遊戲

`make` 成功後，在同一個終端機輸入：

```powershell
.\maze_game.exe
```

開頭的 `.\` 表示執行目前資料夾內的程式。輸入後，遊戲畫面與輸入提示都會出現在下方終端機。

出現 `Rows and columns (odd 5..21):` 時，先輸入兩個整數，例如：

```text
5 5
```

列數和欄數都必須是 5～21 的奇數，兩者不必相同，例如 `5 9` 也有效。無效尺寸會顯示 `Invalid size` 並結束；請重新啟動遊戲。

接著每次輸入一個指令並按 Enter，大小寫皆可。

**遊戲執行期間，你輸入的內容會交給遊戲處理。** 請等遊戲結束、重新出現 `PS ...>` 後，再輸入 `make` 或 `make test`；不要把這些建置指令輸入在 `Command:` 後面。

| 指令 | 功能 |
|---|---|
| W／A／S／D | 上／左／下／右移動一格 |
| Z | 撤銷一次成功移動 |
| Y | 重做一次已撤銷的移動 |
| R | 回到同一張迷宮的起點，重置有效歷史 |
| Q | 結束遊戲 |

地圖符號：`#` 是牆、`.` 是通道、`S` 是起點、`E` 是終點、`@` 是玩家。`@` 只是顯示時覆蓋的位置，不能寫回地圖陣列。玩家可走入任何非 `#` 的有效位置，包括 `S` 和 `E`。

到達終點會顯示 `You escaped in N steps!` 並結束。每次啟動會重新生成迷宮，因此不能假設固定的 WASD 序列一定能通關；R 則不會重新生成地圖。

### 3.5 每次修改後的固定流程

1. 在遊戲中輸入 Q 並按 Enter，回到 PowerShell 提示字元。若程式無法正常結束，可在終端機按 Ctrl+C 中止。
2. 修改 `player.c`，按 Ctrl+S。
3. 在終端機輸入 `make test`，閱讀測試結果。
4. 輸入 `make`，更新遊戲執行檔。
5. 輸入 `.\maze_game.exe`，實際操作。

`make test` 更新的是測試程式；修改後要玩遊戲，仍需執行 `make`，避免執行舊版遊戲。程式執行中先結束再建置，也能避免 Windows 因執行檔仍被占用而無法連結。

在終端機用滑鼠選取需要的輸出，按 Ctrl+Shift+C 複製，再切到 `report.txt`，按 Ctrl+V 貼上並儲存。記錄第 10 節要求的五項畫面，每項附一句話說明。遊戲只需保留通關時的最後地圖、步數狀態與通關訊息，不需要貼上整場遊戲的所有畫面。

## 4. 必要的 C 語言觀念

### 4.1 座標與二維陣列

陣列索引從 0 開始。地圖座標使用 `[row][col]`：列往下增加，欄往右增加。

| 方向 | 列的變化 | 欄的變化 |
|---|---:|---:|
| W 上 | −1 | 0 |
| A 左 | 0 | −1 |
| S 下 | +1 | 0 |
| D 右 | 0 | +1 |

`maze` 的配置容量是 `MAX_ROWS × MAX_COLS`，但本次遊戲只使用 `rows × cols`。判斷是否越界時，應使用本次傳入的 `rows` 和 `cols`。

有效索引需滿足 `0 <= row < rows`、`0 <= col < cols`。C 不會自動阻止陣列越界，所以必須先確認座標有效，再讀取 `maze[row][col]`。例如利用 `||` 的短路求值，將越界判斷放在地圖存取之前；左側條件成立時，後方條件不會繼續求值。

### 4.2 陣列傳入函式的效果

在本專案中，函式透過陣列參數可以修改呼叫端的陣列元素。例如修改 `player[0]`，主程式中的玩家列座標也會改變。

因此，移動時應先把預計的新列、欄放在區域變數，完成所有檢查後再寫入陣列。不要先修改玩家位置，再嘗試於失敗時改回來。

二維陣列參數 `char maze[][MAX_COLS]` 保留欄數，讓編譯器能計算每列的儲存間距。請維持原有函式宣告。

### 4.3 函式回傳值

`move_player` 使用數字向主程式回報結果；顯示 `Blocked` 等訊息由 `main.c` 負責。玩家函式應專注於判斷和更新資料，避免額外讀取輸入或列印畫面。

C 的 `if` 會把 0 視為假、非 0 視為真；但 `move_player` 的負數也是非 0，所以不能用「非 0 就是成功」判斷移動。請依規格區分 `1`、`0`、`-1` 和 `-2`。

## 5. 核心資料結構：玩家與歷史紀錄

```c
int player[2];                 /* [列, 欄] */
int history[MAX_HISTORY][2];   /* 每筆紀錄都是一組座標 */
int state[2];                 /* 目前索引、有效筆數 */
```

| 資料 | 意義 | 初始值 |
|---|---|---|
| `player[0]`、`player[1]` | 玩家目前列與欄 | `[1, 1]` |
| `history[0]` | 起點紀錄 | `[1, 1]` |
| `state[STATE_CURSOR]` | 目前指向哪一筆歷史 | 0 |
| `state[STATE_COUNT]` | 有效歷史筆數，包含起點 | 1 |

`STATE_CURSOR` 和 `STATE_COUNT` 是常數，分別代表 `state` 的索引 0 和 1；真正會改變的資料是對應的陣列元素。

每次操作完成後，應維持以下關係：

```text
1 <= 有效筆數 <= MAX_HISTORY
0 <= 目前索引 < 有效筆數
player 的座標等於 history[目前索引] 的座標
```

畫面的數字由主程式計算：

```text
Steps = 目前索引
Undo  = 目前索引
Redo  = 有效筆數 − 目前索引 − 1
```

Steps 表示目前歷史路線的步數，包含走回曾經經過位置的成功移動；它不是整場遊戲累積按鍵次數，也不一定是到終點的最短距離。

### 5.1 用一個例子理解撤銷和重做

假設某張地圖允許由 `[1,1]` 連續向右兩次，再向下一次：

| 操作後 | 玩家位置 | 目前索引 | 有效筆數 | 可重做次數 |
|---|---|---:|---:|---:|
| 起始 | `[1,1]` | 0 | 1 | 0 |
| D | `[1,2]` | 1 | 2 | 0 |
| D | `[1,3]` | 2 | 3 | 0 |
| S | `[2,3]` | 3 | 4 | 0 |
| Z | `[1,3]` | 2 | 4 | 1 |
| Z | `[1,2]` | 1 | 4 | 2 |
| Y | `[1,3]` | 2 | 4 | 1 |

撤銷和重做只改目前索引及玩家位置，保留歷史內容和有效筆數，因此可以來回移動。

### 5.2 撤銷後的新分支

接續上例，在索引 2 的 `[1,3]` 成功向左移到 `[1,2]`，新紀錄會取代索引 3 原來的 `[2,3]`。目前索引變成 3，有效筆數為 4，此時沒有可重做紀錄。

如果先撤銷更多步，再做成功新移動，有效筆數也應縮短成「新索引 + 1」。超過有效範圍的舊陣列內容不需清空，但程式不能把它當成可重做資料。

撞牆、越界或非法命令沒有產生新移動，不能截斷原本的重做分支。

## 6. 五個函式的作業規格

### 6.1 `move_player`：移動一格

接受 W/A/S/D，大小寫皆可。請依以下順序處理：

1. 用暫存座標表示預計位置，辨認命令；非法命令回傳 `-1`。
2. 檢查目標是否越界或為 `#`；若是，回傳 `0`。
3. 檢查下一筆索引是否小於 `MAX_HISTORY`；若無空間，回傳 `-2`。
4. 全部通過後，才寫入新歷史、更新玩家與目前索引，並將有效筆數設為新索引加 1；回傳 `1`。

所有失敗情況都不得改動 `player`、`history`、`state`；任何情況都不得修改 `maze`。

**容量要看「目前索引 + 1」，不能只看有效筆數。** `MAX_HISTORY` 為 1000，包含起點，因此從起點開始最多保留 999 步。即使有效筆數已滿，撤銷後仍可能有位置可寫入新分支。若目標本來就是牆，即使歷史已滿也應回傳 `0`，因為牆壁判斷先於容量判斷。

Z、Y、R、Q 由 `main.c` 分派處理；若直接傳給 `move_player`，它們都不是有效的方向命令。

### 6.2 `undo_move`：撤銷

- 目前索引為 0：回傳 `0`，所有資料不變。
- 否則：索引減 1，從該筆歷史還原玩家，回傳 `1`。
- 不修改歷史內容或有效筆數，也不以反方向移動取代讀取歷史。

### 6.3 `redo_move`：重做

- 若下一筆索引已達有效筆數：回傳 `0`，所有資料不變。
- 否則：索引加 1，從該筆歷史還原玩家，回傳 `1`。
- 不新增紀錄，也不修改有效筆數。

### 6.4 `reset_player`：重置

依傳入的 `start` 設定玩家與 `history[0]`，將目前索引設為 0、有效筆數設為 1。不要把起點固定寫成 `[1,1]`，因為測試會使用其他起點；不需清空整個 `history`。

### 6.5 `reached_goal`：判斷終點

玩家的列和欄都與 `goal` 相等才回傳 `1`，其餘回傳 `0`。只符合其中一個座標不算抵達，且此函式不應修改資料。

建議實作順序：`reached_goal` → `reset_player` → `move_player` → `undo_move` → `redo_move`。主程式保證狀態已初始化；本次重點是依介面規格操作有效資料。

## 7. 多檔案 C 與 Makefile 教學

### 7.1 從原始碼到執行檔

`.h` 提供函式宣告與常數，讓不同 `.c` 檔共用介面；函式實作放在 `.c`。各個 `.c` 分別編譯為 `.o`，最後連結成遊戲：

```text
main.c      → main.o       ┐
maze.c      → maze.o       ├→ maze_game.exe（Windows）
generator.c → generator.o  │  maze_game（其他平台）
player.c    → player.o     ┘
```

測試使用另一個入口：`player_tests.c` 也有自己的 `main`，它與 `player.o` 連結成 `player_tests.exe`，不需要連結遊戲的 `main.o`。不要用 `gcc *.c` 將所有檔案一起連結，否則會出現多個 `main` 的錯誤。

### 7.2 讀懂一條規則

Makefile 中的實際規則：

```makefile
player.o: player.c player.h config.h
	$(CC) $(CFLAGS) -c player.c -o player.o
```

- `player.o` 是目標，冒號後是依賴檔案。
- 目標不存在，或依賴檔案的修改時間比目標新時，make 會執行下一行命令。
- 命令行需以真正的 Tab 開始。本次無須修改 Makefile。
- `CC = gcc` 指定編譯器；`CFLAGS` 指定共用編譯選項。
- `-std=c11` 選用 C11；`-Wall -Wextra -Wpedantic` 啟用警告。
- `-c` 只編譯成目的檔；`-o` 指定輸出名稱。

遊戲連結規則將四個 `.o` 組合為執行檔。make 本身負責判斷與執行命令，實際編譯和連結由 GCC 完成。

### 7.3 三個常用目標

| 指令 | 行為 |
|---|---|
| `make` | 執行預設的 `all`，建立或更新遊戲 |
| `make test` | 建立或更新測試執行檔，再執行測試 |
| `make clean` | 刪除規則列出的 `.o` 與遊戲／測試執行檔，保留原始碼 |

`.PHONY: all test clean` 宣告這些名稱代表工作，不是一般檔案。因此即使測試執行檔已是最新，`make test` 仍會執行測試。Makefile 也會依 `OS` 選擇 Windows 的 `.exe` 名稱。

### 7.4 觀察增量編譯

請依順序操作並把實際輸出記錄到報告：

1. 第一次執行 `make`：若沒有既有產物，會編譯四個 `.c` 並連結。
2. 不改檔再執行 `make`：通常顯示 `Nothing to be done for 'all'.`。
3. 僅修改 `player.c` 的一段註解並儲存後執行 `make`：觀察是否重建 `player.o` 並重新連結遊戲。這一步不要改動程式邏輯。
4. 執行 `make test`：視需要更新測試使用的目的檔和執行檔，並執行測試。

make 依檔案修改時間判斷是否重建，因此即使只改註解，也會重新編譯對應的目的檔。

例如只修改 `player.c` 後，遊戲建置應出現：

```text
gcc -std=c11 -Wall -Wextra -Wpedantic -c player.c -o player.o
gcc main.o maze.o generator.o player.o -o maze_game.exe
```

可從規則推知：修改 `player.h` 會影響遊戲的 `main.o`、`player.o`，也會影響測試的 `player_tests.o`；實際重建哪些目標取決於執行的是 `make` 還是 `make test`。這是閱讀練習，不需要修改標頭驗證。

### 7.5 清理與重新建置

先結束遊戲和測試程式，再於目前的 `student_starter` 終端機執行：

```powershell
make clean
make
```

`make clean` 會刪除目的檔及執行檔，保留原始碼和報告。檔案已不存在時會跳過，因此可以重複清理。若使用 `mingw32-make` 或 `mingw64-make`，照第 3.2 節替換指令名稱即可。

執行時可能先顯示一整行 `powershell.exe -NoProfile -Command ...`，這是正在執行的清理命令，不是錯誤。若後面沒有錯誤訊息，並回到 `PS ...>` 提示字元，就表示命令已完成。若檔案被遊戲或測試占用，請先結束程式再清理。

## 8. 測試與除錯方法

### 8.1 `make test` 實際做了什麼？

`make test` 會先確認 `player_tests.o` 和 `player.o` 是否需要重建，再連結成測試執行檔，最後執行 48 個檢查。測試使用固定的地圖和狀態直接呼叫函式，不需要手動輸入尺寸或方向，也不使用隨機生成的遊戲地圖。

每完成一個函式都可執行 `make test`。尚未完成其他函式時仍可能出現失敗，請先看與目前功能有關的第一個 `FAIL`。起始骨架預期為 `Tests: 11 passed, 37 failed`；部分檢查通過，只代表暫時回傳值剛好符合某些情境，不代表該功能已完成。

### 8.2 看懂失敗訊息

移動案例會同時檢查命令回傳值、玩家位置及歷史狀態。失敗時會顯示編號、指令和起始位置，並列出預期值與實際值。例如尚未完成的骨架會出現：

```text
FAIL [06]: move 'd' from (1,1): success
  actual state: player=(1,1), cursor=0, count=1
  return: expected=1, actual=-1
  expected state: player=(1,2), cursor=1, count=2
  history[1]: expected=(1,2), actual=(-1,-1)
```

- `[06]`：第 6 個檢查，方便對照測試順序。
- `move 'd' from (1,1): success`：測試情境是從 `(1,1)` 向右，預期移動成功；這裡的 `success` 描述預期行為，不表示本次測試已通過。
- `expected`：規格要求的結果；`actual`：函式實際產生的結果。
- 這個例子中，回傳值、玩家位置、目前索引、有效筆數及新歷史都未符合預期，應先檢查 `move_player`。

如果出現 `history changed`，表示失敗移動改動了歷史；`unrelated history changed` 表示成功移動改動了新紀錄以外的歷史；`maze changed` 表示地圖被修改。

其他情境會顯示行為名稱及實際的 `player`、`cursor`、`count`。例如 `undo changes cursor but preserves count` 表示「撤銷應改變目前索引，但保留有效筆數」。請依名稱判斷要查的規格，再到 `player_tests.c` 搜尋該字串，查看檢查前如何設定狀態，以及檢查哪些條件。

一個 `FAIL` 可能包含多項條件，並不等於只有單一變數錯誤。前一步移動若尚未完成，也可能讓後面的撤銷或分支測試一起失敗；建議按「移動 → 撤銷／重做 → 分支」順序處理。

### 8.3 測試分組與檢查範圍

| 編號 | 終端機分組 | 主要檢查 |
|---|---|---|
| 01～21 | Commands, movement, bounds and history | 大小寫、非法命令、移動、四邊越界、歷史更新與失敗不變性 |
| 22～28 | Undo and redo | 連續撤銷、保留重做位置、起點及末筆的限制 |
| 29～35 | Failed moves and new branches | 失敗後保留重做、成功新分支取代及縮短舊分支 |
| 36～39 | Reset | 回到起點、歷史重置、使用傳入的起點 |
| 40～43 | History capacity | 滿容量拒絕新增、先判斷牆壁、撤銷後可寫入新分支 |
| 44～48 | Goal and map preservation | 終點兩個座標均需相符，整張地圖保持不變 |

### 8.4 如何依結果除錯

1. 先按 Ctrl+S，執行 `make test`，確認測到的是已儲存的程式。
2. 找到第一個與目前功能有關的 `FAIL`，比較預期與實際資料。
3. 在紙上列出「玩家位置、目前索引、有效筆數、有效歷史」，逐步推演該案例。
4. 檢查索引是否差 1、是否先修改後檢查，以及是否誤把有效筆數當成目前索引。
5. 修正 `player.c` 後重新測試，不要修改測試條件來讓結果通過。

`Tests: 48 passed, 0 failed` 表示這 48 個檢查全部通過。仍需依第 6 節確認所有函式符合規格，並實際執行遊戲；自動測試不能取代操作驗證。

測試程式只要有失敗就回傳非 0 結束碼，因此 make 最後顯示 `Error 1` 是在回報測試未通過。請先往上找 `FAIL`，不要把它誤認為 Makefile 語法錯誤。

測試通過後，還要實際執行遊戲：先輸入 `5 5`，確認撞牆與非法命令，完成一次成功移動後依序試 Z、Y、R，最後依該次地圖走到終點。不要只根據編譯成功就認定功能正確。

## 9. 常見問題

| 現象 | 原因或處理方式 |
|---|---|
| `make` 找不到 | 先依第 3.2 節確認是否提供 `mingw32-make` 或 `mingw64-make`，後續一致改用可用名稱 |
| 三種 Make 名稱皆找不到，或 `gcc` 找不到 | 確認工具安裝與 PATH；調整後完整重開 VS Code，再新增終端機 |
| `No makefile found` 或沒有建置目標 | 終端機未位於含 Makefile 的 `student_starter` |
| 執行檔找不到 | 先執行 `make`；PowerShell 使用 `.\maze_game.exe` |
| VS Code 單檔執行出現連結錯誤 | 本專案有多個模組，請在內建終端機使用 `make`，再執行 `.\maze_game.exe` |
| 顯示在「輸出」面板，無法輸入遊戲指令 | 請切換到「終端機」面板，依第 3 節建置並執行 |
| 輸入 `make` 後遊戲顯示非法命令 | 遊戲尚在執行，先輸入 Q，回到 `PS ...>` 再輸入建置命令 |
| 連結出現 `Permission denied`、無法寫入執行檔 | 先結束仍在執行的遊戲或測試，再重新建置 |
| `make test` 通過，但遊戲仍是舊行為 | 按 Ctrl+S 後再執行 `make`，再啟動遊戲 |
| 清理時顯示很長的 PowerShell 命令 | 這是正常的命令輸出；查看後面是否有錯誤，見第 7.5 節 |
| `multiple definition of main` | 把遊戲和測試入口一起連結了，改用 `make`／`make test` |
| `undefined reference` | 檢查函式名稱、介面及是否使用正確建置方式 |
| `missing separator` | Makefile 命令前的 Tab 可能被改成空白，恢復原始 Makefile |
| 修改後沒有重新編譯 | 確認已儲存，且編輯的檔案與終端機位於同一專案 |
| `make test` 最後顯示 Error | 往上看 `FAIL` 與通過／失敗數，先修正功能 |
| 遊戲開始就結束或顯示尺寸錯誤 | 第一筆輸入應是兩個 5～21 的奇數，不是方向命令 |
| 撤銷後不能重做 | 檢查撤銷是否誤改有效筆數或歷史 |
| 撤銷後撞牆卻失去重做 | 檢查是否在確認成功前就更新歷史或有效筆數 |
| 歷史滿後撤銷仍無法新移動 | 應檢查下一筆索引，而非只看有效筆數是否滿 |
